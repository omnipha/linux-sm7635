## Host re-address of a re-enumerated diagnostic gadget (#169, host-only, 2026-10-29)

**Host-only — no flash, partition write, USB session or phone result. #169 stays OPEN for the coordinator-held reboot measurement.** The run-58 host journal shows the concrete miss. At 09:49:39 the gadget returned as `18d1:4ee2`, manufacturer `omnipha`, first registered as `usb0`/`usb1` and then renamed to `enx5ec440cb6dc2`/`enx46b3b6e58925`. NetworkManager logged only those renames. The installed rule was `SUBSYSTEM=="net", ACTION=="add", DRIVERS=="?*", ATTR{../manufacturer}=="omnipha*", RUN+="/usr/local/sbin/omnipha-usb-addr"`. A read-only `udevadm test` of the host `net` device reproduces the path error: `ATTR{../...}` reads the intermediate `.../net` directory, which has no manufacturer, while `ATTRS{...}` reaches the USB device ancestor. The helper therefore did not run and matched no interface. Nothing added `172.16.42.1/24`, and nothing had an address to remove. The name-pinned NetworkManager profiles were not the failing mechanism.

`scripts/90-omnipha-usb-net.rules` keeps that same single helper and changes only the match to the USB ancestor: manufacturer `omnipha`, idVendor `18d1`, idProduct `4ee2`. `scripts/omnipha-usb-addr` remains the only addresser. It claims an interface only when its own driver is `cdc_ncm` or `cdc_ether` and that ancestor is the diagnostic gadget, then appends one line to `/run/omnipha-usb-addr.log`: the interface, driver, address, and `result=added` or `result=failed`. A later run finding the address still present records `keep ... result=already-present`; it never adds a second address. An unrelated driver is not recorded or addressed, and a `cdc_ncm` interface on any other USB identity is recorded as `result=not-gadget` and skipped.

`sh scripts/test-usb-readdress.sh` is the host fixture. It first runs `udevadm test` against the real host `net` sysfs node and requires the ancestor attribute to match while `ATTR{../...}` does not. It then creates `enxnew` (`cdc_ncm`), `enxether` (`cdc_ether`), `enxunrelated` (another driver on the same gadget identity) and `enxforeign` (`cdc_ncm` on another USB identity), all inside one private mount and network namespace. The helper addresses only the first two. A second run after the 150 s window finds the NCM address already present and leaves both unrelated interfaces without an address. No USB device, fastboot operation or image is involved. With `OMNIPHA_CHECK_INSTALLED=1`, it additionally compares the installed rule and helper to the tracked files.

`scripts/observe-usb-addr.sh` is the bounded, read-only live record; it does not add an address or touch a link. For each diagnostic-gadget interface it reports `helper_ran`, `address_added` and `removed` into root-only `/run/omnipha-usb-observe.log`, sampling for 180 s. The fixture exercises it across the full 150 s guard window: it records `removed=no` for NCM, then an intentional ECM removal as `removed=yes`, and never observes the unrelated interfaces. The coordinator starts this observer immediately before the one guest reboot and keeps its output outside Git.

The guest recovery budget is unchanged: `/run/keep` must exist within 150 s, and the self-stage waits at most 145 s for it. The host-side budget is the measured run-58 gap, about 17 s from reboot to gadget registration, plus rule and address setup. The fixture proves the address is still present after the full 150 s window, leaving well above 100 s for SSH, capture and `/run/keep`. The 180 s observer covers that full window. This userspace record cannot detect or recover a kernel hang; the 150 s guard remains the recovery mechanism for that case.

No new image is required and no new flash is justified by this host-only change.
